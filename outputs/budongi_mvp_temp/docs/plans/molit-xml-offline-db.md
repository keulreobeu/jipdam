## 2026-10-12 재검토 대상과 실행 경계

고정 검토 대상: 현재 채팅에 사용자가 붙여 넣은 **서울 전월세·매매 원시 XML 수집과 오프라인 DB 생성**. 기존 Plan 내용은 보존하고 그 계획의 공통 수집기/서비스별 매핑/두 관측 DB/다섯 CLI 구조를 유지한다. 일반 기술 선택과 필요한 검증은 사용자의 목표·실행 정책에 따라 담당자가 수행한다. 외부 리뷰·텔레메트리·원격 동기화는 실행하지 않는다. 사용자 요구에 없는 office-hours·새 구조 선택·체인 탐색 질문은 생략한다.

### 범위 평가와 결정 근거

서울 25구 × 13개월 × 세 API의 원본·정규화·조회 DB·ZIP은 첫 단계로 적절하다. Source Registry의 일반 매매 제외는 기존 구현의 불일치다. 재등록이 끝날 때 범위를 세 API로 일치시키고 키 선택 계약은 그때 확인한다. 기존 rental_v1·sale_observations_v1을 재사용하며 매칭·좌표·시설·추천은 사용자가 후속으로 두었다. 이를 전체 통합 DB 목표 달성으로 표시하지 않는다.

구조 결정: 사용자 계획의 기존 배열 유지. 별도 프런트·서비스·프레임워크를 추가하지 않는다. 공통 수집기·정규화/DB·CLI·staging은 순차 구현한다. 같은 제품 모듈과 문서가 겹치므로 병렬 에이전트를 실행하지 않는다.

### 아키텍처 검토

- [P1] (confidence: 10/10) `source_registry.json`의 일반 매매 `status=excluded`는 계획의 세 API와 다르다. 처분: 사용자가 키 재등록 진행 중이라고 응답했다. 새 호출/키 선택 변경은 완료 통보 후, 이미 있는 원본의 오프라인 검증은 계속한다.
- [P2] (confidence: 9/10) `collection_db.py::_query_input`의 `excluded += 1`은 기간 제외 행의 개별 근거를 남기지 않는다. 처분: 승인된 목표의 제외 사유·추적 요구를 위해 원본 행마다 staging 상태와 이유를 보존한다.
- Raw → 검증된 페이지 → staging(유효/기간 제외/거부) → rental/sales DB → 건수·FK·원본 조인 검사 → 새 출력 게시. 원본은 파서 수정에도 재사용한다.
- 현실적인 실패: 잘못된 필수 값. 정규화 DB를 게시하지 않고 원본 참조·행 위치·사유를 보고하여 수정 후 오프라인 재시도한다.

### 코드 품질 검토

- [P2] (confidence: 9/10) `_query_input`은 첫 오류에서만 보고·중단한다. 처분: 수집 완료 원본의 오류를 모두 기록한 뒤 DB 전체 생성은 거부한다. 유효/제외/거부의 합과 원본 건수가 같아야 한다.
- 공유 계약은 기존 `safe_file`, `verify_query`, `normalize_row`, `observation_id_for`를 사용한다. 새 범용 플러그인 프레임워크·추정 매칭은 추가하지 않는다.
- [P1] (confidence: 9/10) `pack_collection`은 DB batch_id와 해시만 확인하므로 부분 DB 생성 후 수집이 늘어도 잘못된 최신 완료 ZIP을 만들 수 있다. 처분: DB가 참조한 계획·완료 query·원본 해시/위치와 현재 아카이브를 대조하고 stale DB는 재생성을 요구한다.

### 테스트 검토·실행 단위

기존 unittest 9개는 실제 실행에서 통과했다. 합성 성공은 실수집 완료 증거가 아니다.

```text
plan → 범위/기록 검증 [기존]
fetch → 완료 재사용/0건/실패/재개/반사 키 차단 [기존]
build-db → 유효/기간 제외/여러 거부 행 staging → rollback/게시 [보완]
         → source+file+row 조인 / 건수 / FK [보완]
pack → 원본 변조 / stale 부분 DB 거부 → XML 포함 ZIP [보완]
실수집 → 종로 시범 → 무호출 재실행 → 서울 전체 [키 재등록 대기]
```

필요 테스트는 기존 `test_collection.py`를 확장한다. 행별 제외·여러 오류·stale DB의 실제 회귀만 추가하고 기존 테스트를 폐기하지 않는다. LLM·UI·모델 평가 변경은 없다.

### 성능 검토

순차 호출·재개·완료 원본 재사용은 유지한다. 페이지 단위 원본 파싱은 32MiB 응답 상한이 있으며 DB는 서울 규모를 실제 실행하여 시간·건수로 확인한다. staging 추가로 디스크 사용은 증가하지만 원본 추적/실패 감사의 필수 비용이다. 인덱스와 SQLite 트랜잭션을 사용하고 원본 없는 재호출이나 검증되지 않은 병렬화를 추가하지 않는다.

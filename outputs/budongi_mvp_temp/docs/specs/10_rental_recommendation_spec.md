## 목표·현재 상태·적용 범위

신혼·첫집·사회초년생이 예산·직장 위치·생활시설 조건에 맞는 **서울 아파트 단지 후보**를 비교하는 팀 MVP·발표 데모다. [Plan](../plans/rental-recommendation-mvp.md), [ADR](../adr/ADR-003-rental-recommendation-first.md), [문서 Task](../tasks/rental-spec-transition.md), [API 자격증명 보관함 CRED-001](11_api_credential_vault_spec.md)을 따른다.

**CURRENT:** 매매 중심 `serving_v1`, 2023 이하 역사 importer, 세 Data Tool, 단일 로컬 4B Tool Calling, 합성 테스트와 required-fact 평가기가 있다. 추가로 raw MOLIT 전월세 XML 파서와 역사 DB에서 분리된 `rental_v1` 합성·정규화 저장기, provenance/시설 커버리지/검수 매칭 입력 계약이 구현됐다. 합성 스냅샷의 결정적 recommend_rentals·recommend CLI·rental-demo가 구현됐다. 공식 응답 필드·단위 매핑, 실제 수집·단지 매칭, 시설 데이터 수집, 추천 HTTP API·웹 비교는 아직 없다. 이 Spec 승인이나 저장 기반 테스트 통과를 제품 구현 완료로 해석하지 않는다.

**TARGET:** Python·SQLite 단일 앱, 정적 HTML/JS 입력·비교 화면, 결정적 추천과 선택형 로컬 LLM 설명. 실제 데이터 수집·단지 매칭은 별도 보류 해제 전까지 실행하지 않는다. 합성 데모와 검수된 실제 데이터 MVP를 구분한다.

첫 범위 밖: 현재 계약 가능한 매물, 아파트 외 주택, 서울 밖 지역, 실제 통근시간·도보거리, 관리비·대출 포함 총주거비, 청약·공공주택, 치안·소음·전세안전 판정, 지도·대화 세션·외부 배포. RAG·Hybrid·LoRA·다중 모델 Router와 대형 모델 비교는 선택형 후속 연구다.

## RENT-001-REQ-01 후보 추천과 표현

[국토교통부 아파트 전월세 실거래 API](https://www.data.go.kr/data/15126474/openapi.do)는 지역코드·계약월별 체결 거래를 제공한다. 추천은 과거 거래 관측에 근거한 단지 후보이며 현재 매물 유무·입주 가능성·계약 가능 가격을 보증하지 않는다. 동·호 정보가 없는 자료로 특정 세대의 상태를 추론하지 않는다.

기본 결과는 최대 5곳, `limit`은 1~20이다. 1~2곳이면 그대로 표시하고, 0곳이면 빈 목록과 필수 조건으로 후보를 찾지 못했다는 설명을 반환한다. 조건을 자동 완화하거나 개수를 채우기 위한 단지를 생성하지 않는다. 관리비·대출비용 미포함, 직선거리, 관측 기간과 기준일, 현재 매물 확인 불가를 결과에 표시한다.

### RENT-001-AC-01 범위·빈 결과·부분 결과

서울 아파트 후보만 반환하고 기본 5/상한 20을 지킨다. 0·1·2건 결과를 그대로 전달하며 매물 보장·자동 완화·총주거비 확정 표현을 하지 않는다.

## RENT-001-REQ-02 같은 계약의 예산과 최신성

입력은 `rental_type`(`jeonse`/`wolse`), 필수 `max_deposit_krw`(원 정수, 0 이상), 월세의 필수 `max_monthly_rent_krw`(원 정수, 0 이상)다. 전세의 월세 상한은 생략 또는 0이며 양수 입력은 오류다. 월세 금액 0은 전세, 양수는 월세로 분류한다. 원천 누락을 0으로 채우지 않는다.

선택 입력은 서울 내 `districts`, 양수 `area_min_sqm`·`area_max_sqm`이다. 면적 하한이 상한보다 크면 오류다. 예산 상한과 면적 경계는 포함한다. bool·음수·잘못된 타입·비유한 숫자는 거부한다.

관측 기간은 추천 시각이 아닌 고정 스냅샷의 `snapshot_date`에서 12개월 전 같은 날짜(없는 날짜는 해당 월 말일)부터 기준일까지다. 예: 2026-10-06 스냅샷은 2025-10-06~2026-10-06을 사용한다. 미래 계약은 제외한다.

유형·면적·기간에 맞는 관측에서 단지별 최신 계약 1건을 선택한다. 원천에서 확인된 취소는 제외하고, 검수된 정정 연결만 반영한다. 같은 계약일은 안정적인 내부 관측 키로 내림차순 선택한다. 그 **한 계약의** 보증금·월세가 각각 상한 이하일 때만 예산을 충족한다. 최신 계약이 예산을 넘으면 과거의 싼 기록으로 되돌아가지 않는다. 서로 다른 계약의 최저 보증금·최저 월세, 매매가·공급액·전월세 환산값을 합치지 않는다.

### RENT-001-AC-02 예산 경계·계약 쌍

같은 계약의 두 금액을 함께 검사하고 상한과 같은 값은 통과한다. A 계약의 싼 보증금과 B 계약의 싼 월세를 합치는 사례는 실패한다. 누락 금액·타입 오류는 성공하지 않는다.

### RENT-001-AC-03 최신 계약·기간·면적·유형

필터 후 최신 계약을 먼저 선택하고 이후 예산을 검사한다. 기간 밖·미래·다른 유형·다른 면적 거래가 대표 계약이 되지 않는다. 같은 날짜·월말 경계에서도 같은 스냅샷은 동일 관측을 선택한다.

## RENT-001-REQ-03 생활조건의 필수·선호·미확인

`workplace`는 출처·좌표가 검증된 장소 ID 또는 확인된 위경도다. 임의 회사명을 추정 좌표로 변환하지 않는다. 미확정·동명 장소는 명시적 오류로 위치 확인을 요청한다. 시설 종류는 역(`station`), 마트(`supermarket`), 공원(`park`), 병원(`hospital`)이며 직장 조건은 `workplace`다.

`conditions`의 항목은 `kind`, 양수 `max_distance_m`, bool `required`를 받는다. 단지·목적지의 검증 좌표로 직선거리를 계산하고 반경 경계는 포함한다. 시설 조건은 해당 종류의 가장 가까운 검수 시설과 비교한다. 시설 자료의 커버리지·기준일·좌표·매칭이 부족하면 `unknown`이며 시설이 없다고 단정하지 않는다. 완전한 검수 범위에서 반경 내 시설이 없을 때만 `unmet`이다.

필수 조건은 `met`만 통과한다. 선호 조건은 `met`/`unmet`/`unknown`을 분리하고 미확인은 충족 점수에 더하지 않는다. 미지원 시설의 필수 요청은 입력 오류, 선호 요청은 미지원 안내와 `unknown`을 반환한다. 직장 거리 조건에는 `workplace`가 필요하다. 좌표의 거리 계산을 통근시간·도보거리·시설 품질로 확장하지 않는다.

### RENT-001-AC-04 필수 조건·직선거리

필수 미충족·미확인 단지를 제외하고 거리 경계값을 검증한다. 좌표 오류·위치 미확정은 분명한 오류이며 직장·역·시설 거리에 직선거리 표시가 있다.

### RENT-001-AC-05 선호·미지원·커버리지

미확인 선호는 충족 점수에 반영하지 않고 구조화 결과에 표시한다. 커버리지 부족을 시설 부재로 바꾸지 않는다. 미지원 필수는 오류, 미지원 선호는 안내가 있는 미확인으로 구분된다. 웹 표시·CLI/HTTP 일치는 AC-08에서 검증한다.

## RENT-001-REQ-04 재현 가능한 순위와 설명

예산·필수 조건 통과 후보를 선호 충족 수 내림차순 → 직장 거리 오름차순(직장 입력 시) → 대표 계약일 내림차순 → 단지 ID 오름차순으로 정렬한다. 직장 거리가 미확인이면 확인된 거리 뒤에 둔다. 같은 종류의 중복 조건은 입력 오류로 처리해 충족 수를 중복 계산하지 않는다. 순위와 이유는 백엔드가 계산하며 LLM이 바꾸지 않는다.

### RENT-001-AC-06 순위 재현성

같은 요청·스냅샷은 동일한 단지·관측·순위를 반환한다. 점수·거리·날짜·ID 동률과 직장 미확인, 중복 조건에서 정해진 정렬·오류가 재현된다.

## RENT-001-REQ-05 최신 임대차 데이터와 계보

최신 전월세의 raw/normalized/serving은 `data/rental/` 아래 별도 경로·스키마 버전·불변 스냅샷으로 둔다. 기존 `data/historical/serving.sqlite3`, `serving_v1`, 2023 cutoff와 학습 자료는 그대로 보존한다. 보증금·월세는 원 정수, 면적은 ㎡, 계산 거리는 m이다. 현재 raw XML 파서는 태그·원문 문자열을 보존하며, 별도 저장기는 이 계약에 맞게 사전 정규화된 입력만 받는다. 공식 기술문서의 실제 필드와 단위를 확인하기 전에는 원천을 정규화·적재하지 않는다.

[공공데이터포털의 공식 API 페이지](https://www.data.go.kr/data/15126474/openapi.do)는 법정동 코드 앞 5자리와 계약년월 6자리로 지역·기간을 조회하며 응답은 REST/XML이라고 설명한다. 또한 개인정보 보호를 위해 아파트 동·호를 제공하지 않는다고 밝히고, 별도 HWP 기술문서를 참고문서로 연결한다. 이번 구현 시 확인 가능한 정적 페이지에는 HWP 본문/상세 응답 필드표가 표시되지 않았으므로 필드명·단위·개별 거래 ID·취소/정정 필드의 존재를 추정하지 않는다.

필수 추적 정보: 내부 단지 ID·관측 키, 원천 종류·원천 참조(원본 해시와 페이지/행 위치 포함), 계약일, 수집 시각, 확인 가능한 출처 기준일, 스냅샷 ID·기준일, 정규화 버전, 단지·좌표·시설 매칭 근거. 출처가 제공하지 않는 날짜·개별 거래 ID·취소/정정 상태는 미확인으로 둔다. 내부 키를 원천 거래 고유 ID라고 부르지 않는다. 같은 값의 서로 다른 실제 계약을 해시만으로 병합하지 않는다.

현재 API 조회는 당시 시점의 완전한 상태 복구가 아니다. 필드 파싱 성공은 취소 여부 검증이 아니며, 현재 응답·정정 상태의 한계를 화면과 결과에 남긴다. 검수되지 않은 단지 매칭은 추천에 사용하지 않는다. 실제 수집·매칭은 [실데이터 Task](../tasks/rental-real-data.md)의 보류가 해제된 뒤 수행한다. 신규 전월세 adapter의 자격증명은 [CRED-001](11_api_credential_vault_spec.md)에 따라 별도 로컬 암호화 보관함에서 불투명한 자격증명 ID로 선택하고 서버에서만 복호화한다. 웹 브라우저 영속 저장소, LLM, 출력·로그·오류 응답, Git과 임대차/역사 DB에 원문을 넣지 않는다. 기존 역사 CLI·가져오기 스크립트의 환경변수 계약은 유지한다. 저장·교체는 API 호출을 일으키지 않으며 실제 수집은 별도 보류 해제 전까지 금지한다.

### RENT-001-AC-07 원본·날짜·식별·격리

답변 근거를 원본 행까지 추적하고 관측 키와 원천 ID를 구분한다. 확인하지 못한 상태·날짜를 추정하지 않는다. 최신 데이터가 기존 역사 DB·학습에 섞이지 않으며 수집·매칭 보류가 유지된다.

## RENT-001-REQ-06 공통 인터페이스와 로컬 화면

**CURRENT:** 읽기 전용 `recommend_rentals`와 CLI `recommend`가 요청 검증·스냅샷 조회·필터·순위·기본 설명을 수행한다. **TARGET:** 로컬 웹 `POST /api/recommendations`가 같은 계약을 호출한다. 현재 세 Tool의 인자·반환·CLI는 바꾸지 않는다. 전월세 실행 경로의 허용 목록은 `rental_recommendation.RENTAL_ALLOWED_TOOLS`의 recommend_rentals 하나로 분리했다. 기존 LLM의 TOOL_SPECS·세 역사 Tool은 유지하며 전월세 LLM 연결은 후속 Task다. 결과 20행 제한을 적용하고 기존 호출 5회·로컬 모델·타임아웃 경계를 유지한다.

반환은 상태(`ok`/`no_match`), 스냅샷·관측 기간·조회 조건, 행 수, 후보 목록, 안내다. 각 후보는 단지 ID·이름·주소, 대표 관측 키·면적·보증금·월세·계약일, 직장/시설의 직선거리·출처, 조건별 상태, 순위 근거, 미충족·미확인 선호, 원본 참조를 포함한다. 입력 오류·미검수/없는 스냅샷·DB 실패는 성공 빈 결과와 구분한다. HTTP 입력 오류 400, 데이터 준비 안 됨 503, 내부 오류 500은 비밀값 없는 설명으로 표시한다.

화면은 조건 입력과 최대 5곳 기본 비교표를 중심으로 로딩·성공·0건·부분 결과·오류·미확인을 보여준다. Python 단일 앱과 정적 HTML/JS, loopback 바인딩으로 팀 로컬에서 실행하며 별도 프런트 빌드·외부 배포·지도·대화 세션은 추가하지 않는다. 직장 입력 원문을 기본 영구 로그로 남기지 않는다. 전월세 서비스 실행 명령은 구현 시 README에 추가하고 지금 동작하는 것처럼 안내하지 않는다.

### RENT-001-AC-08 공통 결과·화면·오류

CLI와 HTTP는 같은 후보·순위를 전달한다. 입력 오류·없는 데이터·내부 오류·0건이 구분되고 비교표는 근거·미확인·날짜·제외 비용을 보여준다. 현재 세 Tool·CLI 계약은 회귀 없이 유지된다.

## RENT-001-REQ-07 설명의 역할과 평가 경계

추천과 기본 설명은 모델 없이 실행된다. 선택형 로컬 4B LLM은 검증된 후보·순위·조건·수치를 설명한다. SQL·DB 직접 접근·원천 수정·임의 시설 추론·후보/순위/필수 조건 변경은 금지한다. 모델 장애·타임아웃·지원되지 않는 주장·숫자/조건/출처 변경이면 백엔드 기본 설명을 사용한다. 기존 `answer_grounding_v2`가 거리·조건·월세 역할까지 보증한다고 간주하지 않고 신규 검증을 구현한다.

### RENT-001-AC-09 모델 없는 추천·설명 fallback

모델 없이 후보·비교·기본 설명이 실행된다. 월세를 보증금으로 바꾸기, 거리를 시간으로 바꾸기, 미확인 조건의 충족 주장, 순위/출처 변경과 모델 장애는 기본 설명으로 대체된다.

### RENT-001-AC-10 합성·실데이터·기존 평가 구분

기존 역사 Tool·cutoff·EVAL-001 required-fact 지표가 유지된다. 신규 합성 검사·실제 전월세 사람 검수 Golden·전체 claim precision을 구분하고 미측정을 성공으로 세지 않는다. 실제 검수 스냅샷·매칭·시설 커버리지·Golden이 없으면 실제 추천 품질 또는 실데이터 MVP 완료를 주장하지 않는다.

## RENT-001-REQ-08 문서 적용과 구현 완료의 분리

문서 전환은 승인된 Spec·ADR·Plan·영구 Task·원장·작업 규칙과 기존 TARGET를 동기화했다. 이후 제품 구현은 각 영구 Task에서 별도로 진행한다. 기존 CURRENT·SDD-001·EVAL-001 baseline/AC와 환경 수정 이력은 보존한다. 문서 Task와 제품 Task는 각 범위의 실제 증거로 완료하며 제품 AC는 실행 전 체크하지 않는다. 기존 2023 평가 미완료는 보존하되 최신 추천의 선행 조건에서 제거한다.

### RENT-001-AC-11 문서·추적·상태의 일치

신규 요구/AC/Task가 추적 원장에 등록되고 링크·메타데이터·scope 검사를 통과한다. README·AGENTS·프로젝트 스킬·기존 TARGET는 같은 방향과 보류 경계를 가리킨다. 제품 미구현을 CURRENT/검증 완료로 표시하지 않는다.

## 검증 명령과 결과

문서 검증은 [TASK-RENT-DOC-001](../tasks/rental-spec-transition.md#doc-validation)에 기록한다. 제품 AC-01~06의 합성 추천·CLI 검사는 [추천 Task](../tasks/rental-recommendation-cli.md#validation)에 기록한다. 후속 Task: [데이터](../tasks/rental-data-contract.md) → [추천·CLI](../tasks/rental-recommendation-cli.md) → [암호화 API 키 보관함](../tasks/api-credential-vault.md) → [웹 비교](../tasks/rental-web-demo.md) → [LLM·평가](../tasks/rental-explanation-evaluation.md). ## CURRENT 추천·CLI 실행 계약

- 함수: `recommend_rentals(connection, snapshot_id=..., arguments=..., allow_synthetic=False)`. 전월세 Tool dispatcher는 recommend_rentals만 허용한다. 모델 연결·HTTP는 아직 포함하지 않는다.
- 현재 저장기의 quality_status는 synthetic_only/source_unverified다. `--allow-synthetic`을 명시한 봉인된 synthetic_only 스냅샷만 실행하며 source_unverified·없는 DB·역사 DB는 추천 데이터로 사용하지 않는다. 실제 검수 데이터 상태 추가는 후속 데이터 Task에서 수행한다.
- 요청 districts는 서울 자치구 이름(예: 종로구) 또는 법정동 앞 5자리 자치구 코드다. 직장은 확인한 latitude/longitude·verified:true·source·source_ref를 받는다. place_id만 있거나 이름만 입력하면 위치 확정 오류다.
- 시설 source manifest dataset의 `source_date`와 coverage checked_at_utc는 스냅샷 기준 최근 12개월 내에 있어야 한다. 확인 불가·오래된 날짜는 unknown이다.
- coverage complete라는 자치구 목록만으로 경계 밖 반경까지 완전하다고 추론하지 않는다. 사전 검수 범위를 `raw_payload.coverage_area={latitude,longitude,radius_m}`로 제공하고 요청 반경 전체가 그 원 안에 포함되어야 판정한다. 이는 정규화 입력의 검수 메타데이터이며 특정 원천 API 필드라고 주장하지 않는다. 없거나 범위가 부족하면 unknown이다.
- source_status의 알려진 정규화 `cancelled`는 제외하고 None은 미확인으로 유지한다. 기타 상태·정정 연결은 검수 완료 전 오류로 처리한다. 현재 실제 원천 상태 매핑은 미구현이다.
- CLI: `recommend --rental-db PATH --snapshot-id ID --request UTF8_JSON --allow-synthetic`. 상태는 ok/no_match, 오류는 input_error(종료 2)·data_unavailable(종료 3)·internal_error(종료 1)이다. DB는 mode=ro/query_only로 열며 없는 경로에 DB를 생성하지 않는다.
- `rental-demo`는 허구 단지 3개·합성 직장과 요청 파일을 만들고 외부 API를 호출하지 않는다. 기본 요청은 직장 직선거리 필수 조건으로 2곳을 반환하며 역 선호는 자료가 없어 unknown으로 표시한다. 기존 데모 DB를 덮어쓰지 않는다.

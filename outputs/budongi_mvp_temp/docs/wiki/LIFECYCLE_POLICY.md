# Agent Harness — Wiki 자동 생명주기 관리 정책 v1.0

**목적:** 검증된 재사용 가능 지식을 최소한의 문서로 유지하고, 오래되거나 중복되거나 잘못된 문서가 축적되지 않도록 한다.

**기본 원칙:** 새 문서 생성보다 기존 문서 갱신을 우선한다. 문서 수 자체가 아니라 정확성·재사용성·최신성·검색 가능성을 최적화한다.

## 1. 자동화 대상과 판단 시점

### 1.1 판단 이벤트

다음 이벤트가 발생하면 위키 관리 필요성을 평가한다.

| 이벤트 | 수행 작업 |
|---|---|
| Jira Task의 완료 검증 통과 | 작성·갱신 필요성 판단 |
| PR Merge 및 코드 변경 | 관련 문서와 코드의 정합성 검사 |
| API·CLI·설정·데이터 계약 변경 | 영향받는 문서 갱신 |
| 배포 및 운영 절차 변경 | 실제 적용 환경과 문서 버전 확인 |
| 장애 해결 및 재발 확인 | 기존 해결 절차 검색·갱신 |
| 의존성·버전 변경 | 기존 문서의 유효성 재평가 |
| 명시적 문서화 요청 | 작성 가능 여부와 근거 확인 |
| 정기 유지관리 작업 | 중복·노후·깨진 링크·폐기 후보 탐지 |

완료 검증이 끝난 Task는 Jira 완료 처리 이전에 문서화 판단 결과를 기록한다.

단, PR Merge 및 배포처럼 Task 완료 이후 발생하는 변경도 별도로 감지한다.

### 1.2 미해결 문제

- 검증 실패나 원인 미확정 사항은 기본적으로 Task 또는 Incident에 기록한다.
- 재현 가능하고 적용 범위가 확인된 임시 해결법은 '임시 조치'로 기록할 수 있다.
- 임시 조치에는 만료·재검토 조건과 담당자를 지정한다.
- 검증되지 않은 해결책을 공식 해결 문서로 게시하지 않는다.

## 2. 자동 작성 조건

다음 중 하나 이상이 충족되면 문서화 대상 후보로 선정한다.

| 조건 | 구체적인 판단 기준 |
|---|---|
| 반복되는 문제 | 같은 원인의 문제가 두 번 이상 관측되었고 재사용 가능한 해결 절차가 존재 |
| 발견하기 어려운 원인 | 특정 환경·순서·의존성 등 일반적인 오류 메시지로 파악하기 어려운 조건 확인 |
| 운영 절차 변경 | 설치·빌드·실행·배포·복구·백업·데이터 처리·예산 관리 방법 변경 |
| 사용 계약 변경 | API·CLI·설정·스키마·입출력 형식·호환성·제약 변경 |
| 영향이 큰 문제 | 보안·데이터 무결성·서비스 중단·잘못된 결과·비용 사고와 관련된 검증된 대응법 |
| 재사용 가능 기능 | 다른 작업자나 에이전트가 알아야 하는 신규 기능의 사용·설정·검증 방법 |
| 명시적 기록 요청 | 사용자가 재사용 가능한 지식을 기록하도록 요청 |

동일 원인의 반복 판단은 기본적으로 최근 90일을 검색하되, 프로젝트 성격에 맞게 변경할 수 있다. 오래된 이력도 탐색하여 기존 해결 문서가 있으면 우선 활용한다.

### 2.1 작성 제외 조건

다음은 원칙적으로 별도 위키를 생성하지 않는다.

- 단순 오타·서식·문장 수정
- 새로운 사용법이나 대응 지식을 제공하지 않는 단순 리팩터링
- 재사용 가치가 없는 일회성 작업
- 기존 문서에 같은 내용이 이미 정확하게 존재하는 경우
- 검증되지 않은 추정이나 실험 결과
- 개별 작업에만 필요한 실행 로그·진행 기록
- 자동 생성 가능한 API 상세 명세를 동일 내용으로 복사하는 행위

제외 시 Jira Task에 `SKIP` 및 제외 사유를 한 줄로 남긴다.

중요한 변경이 이미 충분히 문서화되어 있다면 새 문서를 작성하는 대신 기존 문서 링크를 연결하고 `LINK_EXISTING`으로 처리한다.

## 3. 지식 분류 및 원본의 책임

정보는 성격에 따라 적절한 원본에 저장한다.

| 문서 유형 | 기록할 내용 |
|---|---|
| Spec | 요구사항, 제약 조건, 수락 기준 |
| ADR | 아키텍처 결정, 선택 근거, 대안과 영향 |
| Task / PR | 구현·변경·검증·작업 이력 |
| Incident | 장애 발생·영향·대응·사후 분석 |
| Wiki / Runbook | 검증된 사용법·운영 절차·문제 해결법 |
| README / API Spec | 코드와 밀접한 설치·인터페이스·실행 계약 |

Wiki는 사용자가 따라 할 수 있는 실용적인 지식을 중심으로 구성한다.

기존 Spec·ADR·API 명세를 장문으로 복제하지 않고 원본을 링크한다.

코드와 함께 버전 관리해야 하는 설명은 저장소 문서를 우선 사용하며, Wiki에서는 해당 버전의 문서로 연결한다.

서로 충돌하는 원본이 발견되면 자동으로 어느 하나를 정답으로 선언하지 않고 검토 대상으로 전환한다.

## 4. 신규 작성·기존 갱신·중복 통합

### 4.1 중복 검색

문서 작성 전 다음을 확인한다.

1. 기존 문서 ID 및 관련 Task·PR 연결
2. 기능·모듈·오류 코드·원인·적용 환경
3. 제목·키워드·태그를 이용한 검색
4. 의미 기반 검색을 이용한 유사 문서 탐색
5. 적용 버전 및 문서의 현재 상태 비교

검색 결과가 누락·불완전하거나 여러 문서가 충돌할 경우 무조건 신규 생성하지 않고 검토 대상으로 등록한다.

### 4.2 처리 규칙

| 상황 | 처리 |
|---|---|
| 완전히 동일한 내용 | 새 문서 생성 없이 기존 문서 연결 |
| 같은 문제의 해결법 보완 | 기존 문서 수정 |
| 기존 기능의 사용법 변경 | 기존 문서 최신화 |
| 동일 원인의 환경별 차이 | 가급적 한 문서에 환경별 절차 통합 |
| 기존 문서가 지나치게 방대 | 독립적으로 검색·실행할 부분만 분리 |
| 실제로 독립된 주제 | 새 문서 생성 |
| 중복 문서 다수 발견 | 대표 문서 선정 후 병합·이전 문서 보관 |
| 해결법이 버전에 따라 상이 | 적용 버전 표시 후 병행 유지 |
| 새로운 ADR이 기존 ADR을 대체 | 기존 ADR을 Superseded로 표시하고 새 ADR 연결 |

### 4.3 문서 수정 안전성

- Wiki의 고유 ID를 유지한다.
- 변경 부분을 기존 내용과 비교한다.
- 수동으로 작성된 내용은 근거 없이 덮어쓰지 않는다.
- 편집 전후 버전과 변경 이유를 기록한다.
- 동시 편집 시 버전 충돌 검사를 수행한다.
- 충돌을 자동 병합할 수 없으면 담당자 검토를 요청한다.
- 동일 이벤트 재처리로 문서가 중복 생성되지 않도록 멱등성을 보장한다.

## 5. 작성 및 게시 품질 기준

공식 위키의 모든 내용은 검증 가능한 근거를 갖추어야 한다.

### 5.1 필수 메타데이터

- 문서 ID 및 제목
- 문서 유형과 소유 프로젝트
- 관련 기능·모듈
- 작성·수정·최종 검증 날짜
- 적용 환경 및 버전
- 담당 소유자
- 현재 문서 상태
- 근거 Task·PR·테스트·Spec 링크
- 다음 재검토 조건 또는 날짜

### 5.2 필수 본문

- 목적 및 적용 범위
- 증상 또는 사용 상황
- 확인된 원인과 미확인 사항 구분
- 실제 실행 가능한 해결·사용 절차
- 주의사항과 예외 상황
- 검증 방법 및 결과
- 관련 원본 문서 링크

원인이 특정되지 않았으면 확정된 것으로 기술하지 않는다.

환경에 따라 절차가 달라지면 명령어나 설정값에 해당 환경을 표시한다.

### 5.3 게시 전 자동 검증

다음 항목을 통과해야 한다.

1. 작성 조건 충족
2. 필수 정보 누락 없음
3. 근거와 문서 내용 일치
4. 비밀키·인증정보·개인정보·민감 로그 포함 여부 검사
5. 기존 문서와 중복 여부 검토
6. 적용 버전 및 호환성 명시
7. 내부 참조 및 관련 링크 유효성 확인
8. 코드·설정·명령어가 해당 환경에서 검증되었는지 확인
9. 게시 대상 및 권한 확인

자동 검증에 실패하면 수정 초안 또는 검토 대기 상태로 전환한다. 검증 실패를 무시하고 게시하지 않는다.

## 6. 위키 생명주기 관리

### 6.1 상태 체계

| 상태 | 의미 |
|---|---|
| DRAFT | 작성 또는 갱신 초안 |
| REVIEW_REQUIRED | 근거·권한·충돌 등 추가 검토 필요 |
| ACTIVE | 검증된 현재 유효 문서 |
| STALE | 최신성이 의심되어 재검증 필요 |
| DEPRECATED | 현재 사용은 비권장이나 일부 환경에서 유효할 가능성 있음 |
| SUPERSEDED | 다른 문서나 새로운 절차로 대체됨 |
| ARCHIVED | 일반 검색과 운영 대상에서 제외해 보관 |
| TRASHED | 복구 가능한 삭제 상태 |

각 상태 변경에는 사유와 근거를 남긴다.

### 6.2 자동 갱신 조건

다음 변경이 발견되면 연관된 문서를 재검증한다.

- 코드·API·스키마·설정·배포 환경 변경
- 기존 해결 방법의 실패 보고
- 새 해결 방법의 검증 완료
- 종속 라이브러리나 도구의 호환성 변경
- 문서와 테스트 결과의 불일치
- 임시 조치의 만료 또는 대체
- 기존 링크·참조 대상의 변경

문서의 마지막 수정 날짜가 오래되었다는 이유만으로 본문을 임의 수정하지 않는다.

### 6.3 정기 검토 주기

기본 권장값은 다음과 같다.

| 문서 종류 | 기본 재검토 주기 |
|---|---|
| 보안·복구·운영 핵심 Runbook | 30일 |
| 자주 변경되는 API·CLI·배포 절차 | 90일 |
| 일반적인 문제 해결·사용법 | 180일 |
| 임시 해결법 | 최대 30일 또는 명시된 만료일 |
| 변경 가능성이 낮은 안정 문서 | 변경 이벤트 중심, 최대 365일 |

재검토 시기는 자동 검증을 다시 수행할 시점이다. 기간이 경과했다는 이유만으로 문서를 자동 삭제하지 않는다.

### 6.4 자동 폐기 조건

다음 중 하나 이상에 해당할 경우 폐기 후보로 분류한다.

- 관련 기능이 완전히 제거됨
- 지원 대상인 모든 버전에서 해당 절차가 무효화됨
- 새로운 문서에 모든 유효한 내용이 통합됨
- 임시 해결법이 정식 해결법으로 교체됨
- 동일 내용을 설명하는 중복 문서임
- 관련 시스템과 소유자가 사라져 사용 범위가 존재하지 않음

폐기 후보는 참조 링크, 사용 여부, 지원 버전, 보존 정책을 확인한다.

### 6.5 삭제 정책

**자동 폐기는 가능하되, 자동 영구 삭제는 기본적으로 금지한다.**

정상적인 처리 순서는 다음과 같다.

`폐기 후보 → 검토 → DEPRECATED / SUPERSEDED → ARCHIVED → TRASHED`

- 기존 문서의 유효한 링크를 보존한다.
- 대체 문서가 있으면 연결한다.
- 일반 검색 및 RAG 검색 대상에서는 비활성화된 문서를 제외한다.
- 지원 중인 환경에서 사용하는 문서는 삭제하지 않는다.
- 감사·법적 보존이 필요한 문서는 정책에 따라 보존한다.
- 휴지통 이동 전에도 인바운드 참조와 소유자·권한을 검사한다.
- 영구 삭제는 명시적 보존 정책과 승인 권한이 존재할 때만 허용한다.

단, 민감정보 노출 문서는 일반 폐기 절차를 기다리지 않는다. 즉시 접근 제한 또는 게시 중단을 수행하고 보안 사고 처리 정책에 따라 정제·삭제한다.

## 7. Jira·Git·Wiki 자동화 연결

### 7.1 작업 흐름

`작업 완료 검증 → 문서화 필요성 평가 → 기존 문서 검색 → 작업 결정 → 작성/갱신/연결/제외 → 근거·보안 검증 → 게시/승인 → Jira 결과 기록 → 검색 인덱스 동기화`

### 7.2 작업 결과 코드

| 코드 | 의미 |
|---|---|
| SKIP | 문서화 불필요 |
| LINK_EXISTING | 기존 문서로 충분 |
| CREATE | 신규 문서 작성 |
| UPDATE | 기존 문서 수정 |
| MERGE | 중복 문서 통합 |
| MARK_STALE | 문서 재검증 필요 |
| DEPRECATE | 사용 비권장 전환 |
| ARCHIVE | 문서 보관 |
| REVIEW_REQUIRED | 사람 또는 담당 에이전트 검토 필요 |
| SYNC_PENDING | 연동 실패로 후속 동기화 대기 |

Task에는 판단 결과, 사유, 대상 문서 ID 및 링크, 검증 근거, 작업 실행 상태를 구조화해 기록한다.

### 7.3 실패 복구

- 동일 작업 중복 실행 방지
- 일시적 네트워크·API 오류에 제한된 재시도 적용
- 반복 실패는 복구 큐에 보관
- 실패 원인과 필요한 조치 기록
- 부분 성공 시 생성 문서를 식별하여 이어서 처리
- 실패한 작업을 성공으로 기록하지 않음

문서가 릴리스 안전성이나 사용 계약에 필수적이면 검증·게시 완료 전 완료 또는 배포를 차단한다.

일반적인 저위험 문서의 외부 동기화 장애는 `SYNC_PENDING`으로 기록하고, 명시된 승인 정책이 있을 때만 완료 예외를 허용한다.

## 8. 자동 게시 권한

| 상황 | 기본 정책 |
|---|---|
| 내부의 낮은 위험도 문서 | 모든 검증 통과 시 자동 게시 허용 |
| 기존 문서의 안전한 경미 수정 | 권한 범위 내 자동 갱신 |
| 운영·복구 핵심 절차 | 검증 근거와 지정된 승인 정책 적용 |
| 보안·개인정보·비용·운영 위험 | 담당자 승인 필수 |
| 외부 공개 공간 | 별도 명시적 게시 승인 필수 |
| 문서 삭제·대량 병합 | 소유자 또는 승인권자 확인 |
| 비밀정보 노출 | 즉시 격리 및 보안 처리 |

인증정보와 개인정보는 작성 전·후에 모두 검사한다.

에이전트에는 필요한 작업에 한정된 권한을 부여한다. 자동 게시 권한이 없는 공간에는 초안만 저장한다.

## 9. RAG 및 에이전트 검색 연동

위키를 하네스의 지식 검색 소스로 사용할 때 다음 규칙을 적용한다.

- ACTIVE 문서를 기본 검색 대상으로 설정한다.
- 적용 버전·환경·검증 시점·문서 상태를 검색 메타데이터에 포함한다.
- 새 문서 게시나 기존 문서 갱신 시 변경된 내용을 재인덱싱한다.
- 폐기·비활성화된 문서는 일반적인 최신 지식 검색에서 제외한다.
- 과거 버전이 필요한 경우에만 명시적인 범위 조건으로 검색한다.
- 통합·대체된 문서의 ID는 유지하고 대체 문서로 연결한다.
- 삭제·접근 제한 시 검색 인덱스와 캐시에도 같은 정책을 적용한다.
- 문서의 출처·권한·버전 정보를 검색 결과에 유지한다.
- 인덱스 동기화 실패 시 최신 상태인 것처럼 응답하지 않는다.

검색 품질 향상을 위해 같은 지식의 단순한 재서술 문서를 대량으로 생성하지 않는다.

## 10. 지식관리 Agent의 책임 분리

| 구성요소 | 책임 |
|---|---|
| Trigger / Observer | Task·PR·배포·장애·정기 점검 이벤트 감지 |
| Documentation Classifier | 문서화 필요성·유형·제외 여부 결정 |
| Knowledge Resolver | 기존 문서 검색·중복 및 변경 영향 탐지 |
| Wiki Writer | 근거 기반 작성·갱신·통합 초안 생성 |
| Evidence / Security Reviewer | 사실·검증 근거·보안·권한 검사 |
| Lifecycle Manager | 최신성 검사·비활성화·보관·삭제 후보 관리 |
| Sync Manager | Jira·Git·Wiki·RAG 인덱스 동기화 |
| Orchestrator | 실행 순서·승인·재시도·실패 복구·감사 기록 관리 |

이 구성요소는 논리적인 책임 단위이다. 반드시 각각 별도의 LLM 에이전트로 구현할 필요는 없다.

규칙 기반 처리가 가능한 판단은 코드로 처리하고, LLM은 의미 비교·지식 정리·모호한 내용의 검토에 우선 사용한다.

## 11. 비용 및 실행량 제한

- 변경 이벤트가 발생한 문서를 우선 검사한다.
- 전체 문서 의미 검색은 필요한 범위에서만 수행한다.
- 변경되지 않은 문서는 불필요하게 재작성하지 않는다.
- 동일 Task·PR 이벤트의 재처리를 방지한다.
- 변경이 잦은 이벤트는 일정 시간 동안 묶어서 처리할 수 있다.
- 문서 작성·수정 횟수보다 유효한 지식의 유지 비율을 중시한다.
- 작업별 LLM 호출량·검색 횟수·실패율을 추적한다.
- 일괄 수정과 대규모 삭제에는 별도 한도 및 승인 정책을 적용한다.

## 12. 품질 모니터링 지표

다음 지표를 주기적으로 측정한다.

- 문서화 판단 정확도와 오탐률
- 중복 문서 발생률
- 검증되지 않은 문서의 게시 비율
- 오래된 문서 비율
- 깨진 링크 및 잘못된 버전 참조 수
- 생성 문서 대비 기존 문서 갱신 비율
- 자동 처리 실패 및 복구 대기 건수
- RAG에서 비활성·구버전 문서를 잘못 검색한 횟수
- 문서 검색 후 문제 해결 성공률
- 승인 대기 시간 및 사용량·비용

문서 생성량 자체를 성과 지표로 사용하지 않는다.

## 13. 필수 검증 시나리오

| 시나리오 | 예상 처리 |
|---|---|
| 코드 오타 수정 | SKIP |
| 같은 오류 원인으로 두 번째 장애 발생 | 기존 문서 UPDATE 또는 CREATE |
| 오류 원인을 추정했지만 미검증 | Task 기록, REVIEW_REQUIRED |
| API 응답 스키마 변경 | 관련 문서 UPDATE |
| 기존 문서가 이미 정확함 | LINK_EXISTING |
| 검증된 임시 해결법 | 만료 조건이 있는 임시 조치 문서 |
| 기존 Runbook 절차 변경 | UPDATE |
| 중복 위키 3개 발견 | MERGE 후 나머지 SUPERSEDED 또는 ARCHIVED |
| 기능 삭제 및 미지원 확인 | DEPRECATE → ARCHIVE |
| 보안키가 문서에 노출됨 | 즉시 접근 제한 및 보안 처리 |
| 문서가 삭제됐으나 RAG에 남아 있음 | 인덱스 정리·동기화 오류 처리 |
| 두 에이전트가 같은 문서를 수정 | 버전 충돌 검증 후 안전하게 재시도 |
| Confluence 연결 실패 | SYNC_PENDING 및 복구 큐 등록 |
| 기존 문서가 과거 지원 버전에서 유효함 | 해당 버전 문서 유지 |
| 외부 게시 권한이 없음 | DRAFT 보관 및 승인 요청 |

모든 테스트의 기대 동작과 실제 결과가 일치해야 운영 적용을 승인한다.

## 14. 최종 운영 원칙

1. **불필요하면 작성하지 않는다.**
2. **기존 지식이 있으면 갱신을 우선한다.**
3. **같은 내용은 중복으로 유지하지 않는다.**
4. **검증된 사실만 공식 지식으로 게시한다.**
5. **기능·코드·환경 변경과 관련 문서를 동기화한다.**
6. **오래된 문서는 검증하고, 불필요한 문서는 보관한다.**
7. **영구 삭제는 예외적으로만 허용한다.**
8. **문서 상태와 검색 인덱스의 일관성을 유지한다.**
9. **모든 자동 변경에는 근거·책임·복구 경로를 남긴다.**
10. **문서의 양보다 신뢰성과 재사용성을 우선한다.**

**최종 정책:** Agent Harness는 작업 완료 후 위키를 무조건 생성하는 시스템이 아니라, 작업 과정에서 확인된 재사용 가능한 지식을 선별하고 기존 문서를 지속적으로 갱신·검증·통합·보관하는 지식관리 시스템으로 동작한다.
